Arquitectura

Cómo se despliega hoy en AWS

Waggo

Fuente: specs/INF-001-despliegue-publico-en-aws.md (estado Implementada, ADR-020). Comprobado el 2026-10-28: https://app.mywaggo.com responde 200 y https://api.mywaggo.com/health/ready responde 200.

Un solo ambiente: producción del piloto. La web se publica como estáticos en S3 detrás de CloudFront; la API corre como contenedor en ECS Fargate con el ALB delante.

La base es RDS PostgreSQL 17 en subred privada con PostGIS. Los secretos viven en Secrets Manager y la autenticación de GitHub a AWS es por OIDC, sin claves guardadas.

Las apps nativas de iOS y Android no están en este despliegue: la spec las deja fuera de alcance (EAS Build, fase CD-3).

waggo-api

Clean Architecture con la regla verificada por pruebas

Waggo

La regla Api → Infrastructure → Application → Domain no es solo una convención: la comprueban pruebas de arquitectura (NetArchTest) que fallan si se rompe.

  • 4 proyectos de producción y 6 de pruebas
  • Cada caso de uso es un Command o Query + Handler + Validator, sin MediatR ni AutoMapper
  • Todo devuelve WaggoResponse<T> con errores, avisos e información
  • Carpetas por tipo y por módulo (ADR-012): 9 módulos de endpoints

Fuente: waggo-api/CLAUDE.md, waggo-api/Tests/Waggo.ArchitectureTests/LayerTests.cs, Directory.Packages.props. Proyectos = carpetas Waggo.* (4) y Tests/* (6).

LayerTests.cs verifica que Domain no dependa de otras capas ni de EF Core o ASP.NET, que Application no dependa de Infrastructure ni de Api, y que los handlers sean sealed y no públicos. Son 7 pruebas de arquitectura.

La decisión de no usar MediatR, AutoMapper ni FluentAssertions está en ADR-006; las pruebas usan Shouldly y NSubstitute.

Una emergencia, de la petición a la respuesta

Waggo
RaiseEmergencyHandler.cs (fragmento) 
if (walk.Status is not (WalkStatus.Accepted
    or WalkStatus.InProgress))
{
    response.AddError(AlertErrors.WalkNotActive);

AlertErrors.cs (catálogo de errores del dominio) 
public static readonly Error WalkNotActive = new(
    "Alerts.WalkNotActive",
    "Solo puedes reportar una emergencia en un
     paseo aceptado o en curso.",
    ErrorType.BusinessRule);

Un error de negocio esperado se acumula en la respuesta (código Alerts.WalkNotActive, HTTP 422); si la operación no puede seguir, se lanza una excepción propia que el middleware traduce, sin exponer el detalle técnico.

Fuente: waggo-api/Waggo.Application/Tracking/Commands/RaiseEmergency/RaiseEmergencyHandler.cs y Waggo.Domain/Errors/Tracking/AlertErrors.cs (fragmentos reales); waggo-api/CLAUDE.md (ADR-007, ADR-009, ADR-010).

Este es el fragmento real que implementa el ejemplo 5 de la spec RF-012 (levantar una emergencia en un paseo que nadie ha aceptado devuelve 422 Alerts.WalkNotActive).

Validación en dos capas (ADR-009): el DTO se valida en la frontera de la API con códigos Request.Required y Request.InvalidValue; las reglas de negocio se validan en Application con códigos del módulo.

Los mensajes públicos están en español y explican cómo corregir; el código y los comentarios están en inglés.

Fuente: waggo-api/.github/workflows/ci.yml y deploy.yml, waggo-mobile/.github/workflows/ci.yml, specs/INF-001. Los workflows de CI existen en los dos repos; el título del PR se valida con pr-title.yml (Conventional Commits).

La idea es que ni una persona ni una IA tengan que acordarse de las reglas: si no se cumplen, el build o el CI falla. Por eso las convenciones están en .editorconfig con severidad warning y TreatWarningsAsErrors activado.

Waggo

if (mode === 'tests' && !isTestFile(path)) {
  console.error('TDD guard: los agentes de pruebas

Fuente: .claude/agents/tdd/*.md (frontmatter con hooks), .claude/hooks/tdd-guard.js (44 líneas), README del workspace. Flujo de commits: test → feat → refactor en la rama; el squash deja uno en main.

El orquestador trabaja outside-in: primero una prueba de aceptación del endpoint, luego dominio y casos de uso. El verificador corre las pruebas y certifica que cada agente tocó solo los archivos de su rol.

Los commits locales por fase (test, feat, refactor) quedan como evidencia del TDD dentro del PR; al integrar con squash queda un solo commit en main.
